Your core architecture—a web dashboard for administration, React Native for handheld waiter devices, local ESC/POS thermal printing over LAN, and an offline-first syncing mechanism—is standard for modern point-of-sale (POS) systems.

However, **your database schema and data handling logic have major design holes.** If you build it with the schema you outlined, your system will suffer from ID collisions, security vulnerabilities, missing order data, and financial discrepancies.

Here is a critical code-level and architectural tear-down of what you must fix, add, and remove.

---

## 1. Fatal Architectural & Logic Flaws

### Flaw A: The Order Schema is Missing Items & Price Snapshots

Your proposed `Order` schema only has `id, date, total amount, ispaid`.

* **The Problem:** How does the kitchen or cashier know *what* was ordered? More importantly, if a burger costs $10 today and you raise the price to $12 tomorrow, changing the menu item price will retroactively ruin all your past sales reports unless you store a **price snapshot** inside the order itself.
* **The Fix:** Embed an `items` array inside each order, storing the item ID, snapshot name, snapshot price, and quantity.

### Flaw B: Offline Sync & ID Collisions

If a waiter’s device loses internet connection:

* **The Problem:** If two waiters create orders offline at the same time, traditional sequential IDs (like Order #101) will collide when both devices try to upload to MongoDB later.
* **The Fix:** Use **UUIDs** (generated on the mobile app) as a `clientOrderId`. When internet returns, the mobile app sends the order to the backend with this UUID. The backend checks if `clientOrderId` already exists (**Idempotency**). If it exists, it ignores the duplicate; if not, it saves it.

### Flaw C: Theft Vulnerability (Missing Order Statuses)

If an order is just `isPaid: true/false`, a corrupt waiter can submit an order, print it to the kitchen, let the customer eat, and then delete the order before syncing to the backend.

* **The Problem:** No audit trail.
* **The Fix:** Introduce an order lifecycle status enum: `SUBMITTED` $\rightarrow$ `IN_KITCHEN` $\rightarrow$ `SERVED` $\rightarrow$ `PAID` $\rightarrow$ `CANCELLED`. Waiters **cannot delete orders**—they can only request a cancellation, which requires a Cashier or Manager PIN, and requires logging a `cancellationReason`.

## 2. Refactored Database Schemas (MongoDB / Mongoose)

Here is how your database tables should actually be structured.

### `users` Collection

*Added `pinCodeHash` for mobile app login, explicit role enums, and `isActive` flag so managers can disable staff without breaking past order history.*

```javascript
{
  _id: ObjectId,
  name: String,
  role: { type: String, enum: ['OWNER', 'MANAGER', 'CASHIER', 'WAITER', 'COOKER', 'BARISTA'] },
  phone: String,
  email: String,
  pinCodeHash: String, // Hashed PIN for mobile app authentication
  passwordHash: String, // Hashed password for web dashboard login
  salaryAmount: Number,
  isActive: { type: Boolean, default: true },
  createdAt: Date
}

```

### `menu_items` Collection

*Added `price`, `category`, and `isAvailable` (your requested `menuavailablity`).*

```javascript
{
  _id: ObjectId,
  name: String,
  category: { type: String, enum: ['FOOD', 'DRINK', 'DESSERT', 'OTHER'] },
  price: Number,
  isAvailable: { type: Boolean, default: true }
}

```

### `orders` Collection

*Completely redesigned to support line-item snapshots, offline UUID tracking, and cashier verification.*

```javascript
{
  _id: ObjectId,
  clientOrderId: String, // UUID generated by React Native app while offline
  tableNumber: String,
  waiterId: { type: ObjectId, ref: 'User' },
  cashierId: { type: ObjectId, ref: 'User' }, // Who processed the payment
  items: [
    {
      menuItemId: { type: ObjectId, ref: 'MenuItem' },
      name: String, // Snapshot: "Cheese Burger"
      unitPrice: Number, // Snapshot: 10.00 (protects against future menu price changes)
      quantity: Number,
      notes: String // e.g., "No onions"
    }
  ],
  totalAmount: Number,
  status: { 
    type: String, 
    enum: ['PENDING', 'KITCHEN', 'SERVED', 'PAID', 'CANCELLED'],
    default: 'PENDING'
  },
  isPaid: { type: Boolean, default: false },
  paymentMethod: { type: String, enum: ['CASH', 'CARD', 'MOBILE'], default: 'CASH' },
  syncStatus: { type: String, enum: ['SYNCED', 'PENDING_SYNC'], default: 'SYNCED' },
  createdAt: Date,
  paidAt: Date
}

```

### `user_attendance` Collection

*Supports custom days off, holidays, and leaves.*

```javascript
{
  _id: ObjectId,
  userId: { type: ObjectId, ref: 'User' },
  date: Date, // Format: YYYY-MM-DD
  status: { 
    type: String, 
    enum: ['PRESENT', 'ABSENT', 'LEAVE', 'HOLIDAY', 'HALF_DAY'] 
  },
  note: String // e.g., "Approved annual break"
}

```

### `user_payments` Collection (Payroll)

*Tracks exact payroll payouts by period to prevent double-paying employee salaries.*

```javascript
{
  _id: ObjectId,
  userId: { type: ObjectId, ref: 'User' },
  paymentDate: Date,
  periodMonth: Number, // 1 - 12
  periodYear: Number,  // e.g., 2026
  baseSalary: Number,
  paidAmount: Number,
  processedBy: { type: ObjectId, ref: 'User' } // Manager or Owner ID
}

```

## 3. What to Add & Remove

### What to REMOVE:

1. **Remove hard user deletions:** If a Manager clicks "Delete User", **do not delete the document from MongoDB**. If you hard-delete a waiter, all past order reports tied to that `waiterId` will crash or show orphan data. Instead, set `isActive: false` (Soft Delete).
2. **Remove client-side total price calculation:** Do not let the mobile app calculate the order total and send just `totalAmount` to the backend. The backend must independently calculate `totalAmount = sum(quantity * price)` to prevent compromised clients from sending manipulated bill totals.

### What to ADD:

1. **LAN Printer Relay / Fallback:** Waiters' phones sending raw TCP sockets directly to an ESC/POS printer over local Wi-Fi will fail if the Wi-Fi signal drops inside the dining area. Have the app write to a local SQLite database (using `WatermelonDB` or `expo-sqlite`). If the LAN print fails, the app flags the print queue and retries when reconnected.
2. **Role-Based API Middleware (RBAC):** On the Node.js backend, enforce route permissions strictly:
* `POST /api/users` $\rightarrow$ Accessible **only** by `OWNER` or `MANAGER`.
* `DELETE /api/users/:id` $\rightarrow$ Accessible **only** by `OWNER`.
* `PATCH /api/menu` $\rightarrow$ Accessible by `OWNER` or `MANAGER`.
* `POST /api/orders` $\rightarrow$ Accessible by `WAITER`, `CASHIER`, `MANAGER`, `OWNER`.

## 4. How the Offline Sync Engine Should Work

```
[ Waiter Mobile App ]
        │
        ├─► 1. Saves Order to Local Mobile DB (SQLite) with UUID & status 'PENDING_SYNC'
        ├─► 2. Triggers LAN Thermal Print to Kitchen (over local IP)
        │
   [ Network Check ]
        │
        ├──► (Offline) ──► Waits for internet connection event.
        │
        └──► (Online) ───► POST /api/orders/sync
                                │
                                ▼
                       [ Node.js Backend ]
                                │
                                ├─► Checks if UUID exists in MongoDB
                                ├─► Stores Order & recalculates total
                                └─► Web Dashboard (Socket.io) receives order instantly

```
